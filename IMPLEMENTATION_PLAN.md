# План разработки CryptoCore: восемь спринтов

Дата: 2026-11-06. Целевая среда: Python 3.14, Windows, PyCharm. Это базовый план восьми спринтов. С1–С3 реализованы по порядку; отчёты SPRINT1_REPORT.md–SPRINT3_REPORT.md фиксируют контрольные точки. S3-TEST-3 закрыт реальным NIST STS 2026-11-09; С1–С3 приняты (57/57 Must). С4–С8 не начинались.

Источники: [матрица](REQUIREMENTS_MATRIX.md), [реестр противоречий](REQUIREMENTS_CONFLICTS.md), [архитектура](ARCHITECTURE.md), [силлабус](requirements/syllabus_scientific_ru.md). Полные ID сохраняют привязку к спринтам; все перечисленные ниже группы означают **все** строки группы в соответствующем исходном документе, включая подпункты.

## Правила исполнения и приёмки

1. Порядок: Must текущего и ранее завершённых спринтов → необходимые для их проверки Should → остальные Should → выбранные Could. Бонусы не заменяют обязательные работы. CMAC, BLAKE2b, автоимя output, дополнительный ввод пароля и бенчмарки Could пока не выбраны.
2. Каждое требование имеет статус «Не реализовано / Не проверено», пока нет реализации и доказательств. Для смены статуса указать в матрице тест/команду, среду, результат и ссылку на отчёт или commit. Наличие функции или документа само по себе не доказывает функциональное требование.
3. В конце каждого спринта выполнить его приёмочные проверки и регрессию предыдущих. Любой провал обязательной проверки блокирует приёмку. Отсутствующий OpenSSL/STS, пропуск, непроверенная платформа или противоречивый вектор — открытый пункт, а не успех.
4. Тесты — `unittest` из стандартной библиотеки, CLI — через `subprocess` со списком аргументов без shell. Для криптографии необходим только PyCryptodome как поставщик AES-примитива; версии зависимостей выбрать и зафиксировать после проверки Python 3.14. Для этапа 1 пользователь разрешил установку зависимостей в существующее виртуальное окружение; проверенные версии зафиксированы в pyproject.toml и README.
5. Автоматические тесты должны работать с временными каталогами, бинарными файлами, путями Windows, пробелами и кириллицей. Не требовать GNU-команд для обычного запуска. Внешние инструменты проверяются отдельно и сохраняют собственные версии/параметры в отчёте.
6. Спринты завершаются последовательными контрольными точками, без выдуманных сроков. Перед спорной частью сверяться с C01–C28. Рекомендация в реестре не является согласованной правкой исходника.

## Спринт 1 — каркас CLI и AES-128 ECB

Источник: [m1.md](requirements/sprints/m1.md), 16 Must / 3 Should / 1 Could. Охват: S1-STR-1…STR-4, CLI-1…CLI-5, CRY-1…CRY-5, IO-1…IO-3, TEST-1…TEST-3.

Порядок работ:

1. Создать локальный Git-репозиторий, согласовать размещение удалённого репозитория, если потребуется. Сейчас `.git` отсутствует. Использовать подготовленный `.gitignore`.
2. Создать `pyproject.toml` с пакетом `src/cryptocore`, Python 3.14 и console entry point `cryptocore`. Проверить доступность подходящего PyCryptodome и упаковочных инструментов; зафиксировать проверенные версии. Добавить README: описание, установка/сборка, зависимости, рабочий вызов CLI.
3. Реализовать `argparse`: `aes`, `ecb`, ровно один флаг операции, строго 16-байтный hex-ключ, вход и обязательный выход. Ошибки → `stderr`, ненулевой код. Решение C01: автоимя выхода отложено.
4. Добавить тонкий адаптер `Crypto.Cipher.AES` для одного блока. Собственный AES запрещён. На его основе написать ECB и проверяемое PKCS#7; библиотечный готовый режим не заменяет учебную реализацию.
5. Добавить бинарный файловый ввод/вывод и обработку ошибок. Не публиковать результат расшифрования с некорректным padding.
6. Подготовить тесты и исполняемые примеры README. Начать модульные тесты и KAT уже сейчас, не откладывая их до С8.

Приёмка:

- Полный цикл возвращает побайтово исходные данные: пустой файл, текст UTF-8, произвольные байты, длины 1, 15, 16, 17, 31, 32. Проверить полный блок padding при кратной длине и пустом входе.
- Негативные проверки: нет/оба флага операции, неверный hex/длина ключа, неизвестные режим/алгоритм, отсутствующий файл, отказ записи, усечённый шифртекст, неверный PKCS#7.
- S1-TEST-2: сценарий полного цикла в README. S1-TEST-3: сравнение с OpenSSL с одинаковым padding (C06); сырой NIST KAT проверять без файлового padding.
- Сверить S1-STR и `.gitignore`; результат приёмки занести в матрицу. Готовность к С2 — все 16 Must подтверждены.

## Спринт 2 — CBC, CFB-128, OFB, CTR и файловый IV

Источник: [m2.md](requirements/sprints/m2.md), 19 Must / 2 Should. Охват: S2-STR-1…STR-3, CLI-1…CLI-3, CRY-1…CRY-4, IV-1…IV-4, IO-1…IO-3, TEST-1…TEST-4.

Порядок работ:

1. Сохранить API и приёмку ECB. Разместить четыре собственных режима в `modes/` поверх AES-блока. CFB — полноблочный 128 бит; OFB/CTR/CFB — без padding и с неполным последним фрагментом; CBC — PKCS#7.
2. Для шифрования генерировать IV через `os.urandom(16)`, отклонять пользовательский `--iv` (C03). Файл четырёх новых режимов: `IV16 ∥ C`; ECB остаётся без IV (C04).
3. Реализовать два явных пути расшифрования: префикс без `--iv`, сырой OpenSSL-шифртекст с переданным hex-IV (C05). Проверять длину IV и короткий заголовок. Уточнить CTR big-endian increment и граничные значения счётчика.
4. Обновить README, реализовать адаптер совместимости, который отделяет IV от C и не использует Unix-команды (C07, C28).

Приёмка: для каждого режима полный цикл на граничных длинах, KAT NIST SP 800-38A, сохранение длины потоковых режимов, проверка IV-префикса и ошибок. Обязательно оба направления CryptoCore ↔ OpenSSL для всех четырёх режимов; записать подробные команды/сценарий S2-TEST-4. Повторить С1. Готовность к С3 — все 19 Must и прежние Must подтверждены.

## Спринт 3 — единый CSPRNG, генерация ключей и NIST STS

2. Перевести все IV на этот модуль. Ключ при шифровании сделать необязательным; если отсутствует — сгенерировать 16 байт и сразу ровно один раз напечатать hex с меткой в `stdout`. Ключ не включать в шифртекст; при расшифровании требовать явный ключ (E01).
3. Should: предупреждать о нулевом/последовательном пользовательском ключе в `stderr`, не менять его. Добавить базовую проверку распределения как дополнительный эксперимент.

5. Описать свойства и ограничения CSPRNG, пример сохранения выведенного ключа, процедуру/результаты STS в README/TESTING.

Приёмка: полный цикл с извлечением сгенерированного ключа из stdout; вывод ровно один раз, ключ отсутствует в контейнере; 1000 ключей без повторов; обработка имитированного отказа `os.urandom`; подтверждение использования общего RNG для IV. Обязательно фактический запуск STS и сохранённый отчёт S3-TEST-3; генерация файла не закрывает этот Must. Выполнить все тесты совместимости С2 и регрессию С1.

## Спринт 4 — потоковые SHA-256 и SHA3-256

Источник: [m4.md](requirements/sprints/m4.md), 21 Must / 2 Should / 2 Could. Охват: S4-STR-1…STR-4, CLI-1…CLI-5, HASH-1…HASH-6, IO-1…IO-4, TEST-1…TEST-6.

Порядок работ:

1. Реализовать SHA-256 с нуля по FIPS 180-4: состояние, константы, раунды, 512-битные блоки, padding и длина. Отдельно SHA3-256 с нуля по FIPS 202: Keccak, sponge, доменное дополнение. Выбор SHA3 снимает расхождение с С8 (C08); Could библиотечного второго хеша не выбран.
2. Оба хеша предоставляют потоковые `update`, `digest`, `hexdigest`. Удерживать только состояние и неполный блок; не собирать весь файл в памяти.
3. Добавить подкоманду `dgst`, `--algorithm sha256|sha3-256`, `--input`, текстовый `--output`. Без файла результата печатать `hash` в нижнем регистре, два пробела, исходный путь и перевод строки. Аргументы шифрования отвергать. Для примеров `--input -` поддержать бинарный stdin в `dgst`; это поведение вытекает из примеров С4, не распространять его автоматически на остальные команды.
4. Обновить упаковку и README, указать свойства безопасности хешей. Подготовить проверенные векторы с происхождением; примеры-заглушки не считать KAT.

Приёмка: все выбранные официальные NIST-векторы для обоих хешей с полным учётом предоставленного набора; пустой файл; границы блоков/padding; одинаковый digest при разных разбиениях `update`; формат stdout и `--output`; файловые ошибки. Фактически вычислить хеш файла **больше 1 ГБ**, сравнить с эталоном и измерить ограниченное потребление памяти. Проверить совместимость с системными утилитами; при их отсутствии в Windows подготовить отдельную доступную среду и сохранить её отчёт, не объявлять проверки пройденными заранее. Should: лавинный тест с изменением одного бита. Could бенчмарков отложен. Повторить прежние тесты.

2. Расширить `dgst` флагом `--hmac`, hex-ключом произвольной длины, текстовым выходом и `--verify`. Ключ без HMAC отвергать (E02). Формат HMAC — один пробел перед путём, согласно S5-CLI-3.

Обязательны успешная проверка собственного HMAC, отказ после изменения байта файла, отказ с другим ключом, форматы `--verify`/`--output` и корректные коды завершения. Выполнить регрессию хешей и шифрования.

## Спринт 6 — Encrypt-then-MAC и GCM

Источник: [m6.md](requirements/sprints/m6.md), 27 Must / 1 Should. Охват: S6-STR-1…STR-4, CLI-1…CLI-5, AEAD-1…AEAD-6, IO-1…IO-4, TEST-1…TEST-9.

До реализации: уточнить рамку Encrypt-then-MAC (C18), зафиксировать внешнее nonce-поведение (C05), способ OpenSSL-проверки (C16) и уровень проверки огромного AAD (C14). Не закрывать эти вопросы предположением в коде.

Порядок работ:

1. Составная функция Encrypt-then-MAC: режим шифрования + собственный HMAC. Разные ключи передаются явно; не зависеть от будущего С7 (C17). MAC проверять до выдачи plaintext. Тестировать композицию на библиотечном уровне без нового CLI.
2. Написать GCM с нуля: CTR со специальным inc32, GHASH, GF(2^128) и полином из S6-AEAD-3, обработка AAD/длин и J0. AES остаётся библиотечным примитивом. Другие длины nonce поддержать в API; обычный CLI использует 12 байт.
3. Добавить `--mode gcm` и hex `--aad` с пустым значением по умолчанию; nonce генерировать через CSPRNG. Выход — `nonce12 ∥ C ∥ tag16`, без padding. Поддержать чтение nonce по согласованному правилу `--iv`.
4. Спроектировать потоковую проверку так, чтобы до подтверждения тега не публиковались plaintext и файл назначения. При необходимости сохранять стабильную копию **шифртекста**, затем проверять и только после успеха расшифровывать. Существующий выходной файл при провале оставлять нетронутым.
5. Обновить README, упаковку и описание отказа аутентификации. Для больших AAD тестировать потоковый API, не пытаться передать гигабайты через аргумент shell.

Приёмка: NIST GCM KAT с разными длинами AAD/plaintext/nonce, полный цикл, пустые данные/AAD, большие AAD при ограниченной памяти; изменение AAD, C, nonce, тега и ключа; короткий контейнер. При каждом отказе — ненулевой код, понятная ошибка, отсутствие plaintext в stdout/файле, сохранность существующего результата. 1000 nonce без повторов. Аналогичные проверки обязательны для Encrypt-then-MAC. Should OpenSSL-проверку выполнить через согласованный рабочий адаптер, поскольку в С8 она становится Must. Регрессия С1–С5.

## Спринт 7 — PBKDF2-HMAC-SHA256 и иерархия ключей

Источник: [m7.md](requirements/sprints/m7.md), 22 Must / 3 Should / 1 Could. Охват: S7-STR-1…STR-4, CLI-1…CLI-5, KDF-1…KDF-5, IO-1…IO-4, TEST-1…TEST-8.

Блокер приёмки: C19 — RFC 6070/SHA-1 против требуемого SHA256; согласовать корректные SHA256 KAT для С7 и С8. Не реализовывать дополнительный SHA-1 ради неправильного примера.

Порядок работ:

1. Собственный PBKDF2 по RFC 2898 на HMAC-SHA256 С5: U1 с INT32_BE(i), цепочка Uj, XOR, конкатенация и точное обрезание. Поддержать пароли/salt переменной длины, параметры до 1M итераций, численные ограничения и ошибки.
2. Реализовать `derive_key(master_key: bytes, context: str, length: int) -> bytes` через HMAC(master, UTF8(context) ∥ counter32_be). Это заданная курсом иерархия, не полная реализация HKDF RFC 5869. Подключить разделение encryption/authentication для композиции С6, не меняя форматы файлов.
3. Добавить `derive`: пароль UTF-8, строгий hex-salt или генерация 16 байт через CSPRNG, default iterations=100000, length=32, algorithm=pbkdf2. Вывод без `--output`: `KEY_HEX  SALT_HEX`; с флагом писать только сырые байты ключа, salt не добавлять в файл и обеспечить его доступность пользователю по документированному правилу вывода.
4. Should: `--output` входит в план; освобождать ссылки на пароль как можно раньше, явно описав ограничение очистки памяти Python. Could чтения из файла/окружения пока отложен.
5. Обновить README и упаковку; команды OpenSSL задают SHA256 и hexsalt, сравнивают байты (C20).

Приёмка: согласованные SHA256 KAT, независимое сравнение с OpenSSL, повторяемость при одинаковых параметрах, длины 1–100 байт, произвольные допустимые password/salt, ошибки iterations/length/hex. Для иерархии — детерминизм, разные контексты и длины больше 32 байт. 1000 случайных salt без повторов. Проверить бинарный файл ключа и отсутствие salt в нём. Should S7-TEST-8: замеры 10k/100k/1M с описанием среды. Приёмка не завершается, пока C19 не разрешён и Must-тесты не выполнены.
